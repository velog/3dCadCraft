# Файлов формат `.3dcadcraft` и модел на проекта

> Статус: **реализиран, версия 1** (`src/document/`). Тестове: 11 теста за запис/четене, връзки, Pack и Append.

## 1. Изискванията

1. **Копиране без загуби.** Проектът трябва да може да се копира, изпраща и архивира като **един файл**, без да се „губят“ части.
2. **Повторна употреба (reuse).** Стандартни детайли (болтове, профили, корпуси) да се ползват в много проекти, без да се копират ръчно.
3. **Сигурност на данните.** Срив, спиране на тока или пълен диск по време на запис не трябва да повреждат проекта.
4. **Работа с git и с екип.** Промените трябва да се виждат като разлики (diff), без огромни бинарни файлове при всяка промяна.
5. **Отворен формат.** Файлът трябва да е четим и без 3DCadCraft: стандартен контейнер и документиран формат.

## 2. Сравнение на подходите

| | Autodesk Inventor | Blender | FreeCAD | Onshape | **3DCadCraft** |
|---|---|---|---|---|---|
| Единица за съхранение | по един файл на документ (`.ipt`, `.iam`, `.idw`, `.ipn`) + проектен файл `.ipj` | един `.blend` с много „datablocks“ | един `.FCStd` (ZIP) на документ | облачен документ с табове | **един `.3dcadcraft` (ZIP) с много документи** |
| Препратки между файлове | по път към файла; търсене по пътищата от `.ipj` | **Link** (жива връзка) и **Append** (копие) | App::Link по път | връзки към **версия** на друг документ | **Link / Append / Pack** по UUID + относителен път |
| Копиране на проект | рисковано, нужен е *Pack and Go* | лесно (*Pack Resources*) | лесно за един документ | не е приложимо (облак) | **копира се един файл** |
| Идентичност | име/път на файл | име на datablock | вътрешни имена | ID | **UUID на проект и документ** |
| Резервни копия | `OldVersions/` | `.blend1`, `.blend2` | `.FCBak` | история в облака | **атомарен запис + `.bak`** |
| Работа с git | слабо (бинарни файлове) | слабо (бинарен файл) | средно | не е приложимо | **разпакувана папка с JSON** |

### Проблемът на Inventor

В Inventor сглобката (`.iam`) помни *пътищата* до детайлите (`.ipt`). Ако копираш само сглобката или преместиш папките, при отваряне получаваш „Resolve link“ диалози. Решенията са *Pack and Go*, проектните файлове `.ipj` и Vault, но всяко добавя сложност.

### Какво прави Blender добре и къде куца

Blender пази всичко в един `.blend`, а повторната употреба става с **Link** (жива връзка към обект в друг `.blend`) и **Append** (копие). С *Pack Resources* вгражда външните ресурси. Това е много удобно и е причината моделът да ни хареса.

Слабостите му са три:

1. Препратките са **по име**, така че преименуване в библиотеката чупи връзката.
2. Файлът е **бинарен** и **монолитен**: всеки запис го пренаписва целия, а git вижда само „файлът се промени“.
3. Няма „вид документ“. За CAD трябват детайл, сглобка и чертеж с ясни роли.

## 3. Съветът: да, моделът на Blender, с пет подобрения

**Препоръката е да следваме Blender** (един файл на проект, Link/Append/Pack) с тези подобрения. Всички са **реализирани** във версия 1:

1. **UUID вместо имена.** Всеки проект (`ProjectId`) и документ (`DocumentId`) има глобално уникален идентификатор. Преименуването и пренареждането не чупят нищо. При Link се проверява и дали намереният файл е *същият* проект, а не просто файл със същото име.
2. **Типизирани документи.** Един проект съдържа `Part` (детайл) и `Assembly` (сглобка). Чертежи и презентации се добавят като нови видове без промяна на контейнера.
3. **ZIP с JSON вътре.** Форматът е стандартен (като `.FCStd`, `.3mf`, `.docx`), отваря се с всеки архиватор и всеки документ е отделен запис.
4. **Разпакувана форма за git.** Същата структура може да се запише като **папка** (`Save as folder`). Всеки документ е отделен JSON файл, така че git показва точно какво се е променило. `Project::load` отваря и двете форми.
5. **Атомарен запис.** Записва се във временен файл, който след това замества стария с едно преименуване. Предишната версия остава като `.bak`.

### Кога един файл НЕ е най-добрият избор (честно)

- **Много хора работят по един голям продукт.** Inventor+Vault позволява „check-out“ на отделни детайли. При нас решението е да разделите продукта на **няколко проекта-библиотеки** (по подсистеми), свързани с Link, и да ги държите в git в разпакувана форма.
- **Огромни данни** (облаци от точки, текстури, кеширани мрежи). JSON не е подходящ за тях. Предвидено е такива данни да стават **отделни бинарни записи** в същия ZIP, които се зареждат при нужда. Форматът вече игнорира непознати записи, така че това е обратно съвместимо.

### Следващо подобрение: Link към версия (идея от Onshape)

Днес Link е „жива“ връзка: промяна в библиотеката веднага се отразява навсякъде. Това е удобно, но и опасно, защото някой може да промени стандартен болт, без да знае кои проекти ще засегне. Предлагам в следваща версия на формата `LibraryLink` да пази и **отпечатък (hash) на версията** на свързания документ. При промяна ще излиза „Библиотеката е променена — обнови / остави старата версия“. Това е еквивалентът на Inventor „Update“ и на Onshape „linked document versions“.

## 4. Структура на файла (версия 1)

```text
name.3dcadcraft            ← пакетирана форма: ZIP архив (по подразбиране)
name.3dcadcraft/           ← разпакувана форма: папка със същата структура
├── mimetype               "application/vnd.3dcadcraft.project+zip" (първи, некомпресиран)
├── manifest.json          версия на формата, проект, индекс на документите, библиотеки
└── documents/
    ├── <uuid>.json        един файл на документ
    └── …
```

### `manifest.json`

```json
{
  "format": "3dcadcraft",
  "format_version": 1,
  "generator": "3DCadCraft 0.1.0",
  "project":   { "id": "9c35a810-…", "name": "Bracket" },
  "documents": [
    { "id": "97493bf2-…", "name": "Plate", "kind": "Part",     "file": "documents/97493bf2-….json" },
    { "id": "bff8cb0e-…", "name": "Stack", "kind": "Assembly", "file": "documents/bff8cb0e-….json" }
  ],
  "libraries": [
    { "id": "…", "path": "../lib/fasteners.3dcadcraft", "project": "…", "name": "Fasteners" }
  ]
}
```

Индексът позволява на инструменти (търсачка, файлов мениджър, агент) да видят съдържанието, без да четат всички документи.

### Документ

- **Part:** `sketches` (скици с равнина, геометрия и ограничения) и `body` (B-Rep тяло). Когато се появи дървото на операциите (feature tree), то става източникът на истината, а `body` става кеш, който може да се регенерира.
- **Assembly:** `occurrences`. Всяка съдържа име, `component` (препратка `DocRef`), трансформация и флаг `grounded`. Един детайл, поставен 50 пъти, се пази **веднъж**.

`DocRef { library: None, document }` означава документ в същия проект. `DocRef { library: Some(id), document }` означава документ в свързана библиотека.

## 5. Операции за повторна употреба

| Операция | Какво прави | Кога се ползва |
|---|---|---|
| **Link** (`Resolver::link`) | Добавя препратка към документ в друг `.3dcadcraft`. Нищо не се копира. | Стандартни/фирмени детайли, които трябва да се обновяват централно. |
| **Append** (`Resolver::append`) | Копира документа **и всичко, от което зависи** (локално или от библиотеки) с нови UUID. Споделен компонент се копира веднъж. | „Вземи този възел и ще го променя по свой начин.“ |
| **Pack** (`Resolver::pack`) | Заменя всички Link с локални копия и премахва връзките. Проектът става напълно самостоятелен. | Преди изпращане на клиент/доставчик, при архивиране на поръчка (≈ *Pack and Go*). |

### Как се намира свързана библиотека

1. `<папка на проекта>/<записан относителен път>` — нормалният случай. Работи и при преместване на цялото дърво от папки.
2. `<папка на проекта>/<име на файла на библиотеката>` — когато библиотеката е копирана до проекта (например двата файла са пратени по имейл).

И в двата случая се проверява `ProjectId`. Ако на мястото има *друг* проект със същото име на файла, връзката **отказва** с ясна грешка, вместо тихо да ползва грешните данни.

Пътищата винаги се пазят с `/`, така че файловете се местят между Linux, Windows и macOS без промяна.

## 6. Гаранции на записа

| Гаранция | Как е постигната |
|---|---|
| Атомарност | запис във временен файл `.name.tmp-<uuid>`, `fsync`, после `rename` върху целевия файл |
| Резервно копие | предишната версия става `name.3dcadcraft.bak` (изключва се със `SaveOptions { backup: false }`) |
| Детерминизъм | фиксирани времена в ZIP и стабилен ред: еднакъв проект дава **еднакви байтове**, т.е. няма фалшиви „промени“ в git/Dropbox |
| Точни числа | `serde_json` с `float_roundtrip`: координатите се възстановяват **бит по бит** |
| Версиониране | `format_version` и `format_revision` — виж §6а |
| Защита от zip slip | документите се четат само по име, изведено от UUID, никога по път, взет от файла |
| Валидация при четене | уникални ID, всички препратки сочат съществуващи документи, няма цикли в сглобките |

## 6а. Нови версии на програмата и стари файлове

Два номера в `manifest.json`:

| Номер | Кога се вдига | Какво става при отваряне |
|---|---|---|
| `format_version` (сега 1) | несъвместима промяна: преименувано или премахнато поле, друго значение на стойност | **по-стар файл** → миграция в `document::format::load_with` (по номера), после се чете; **по-нов файл** → отказ „uses format vN; this build reads up to vM“ |
| `format_revision` (сега 9) | добавено нещо, което по-стара програма не може да прочете (нов вид закръгление, нов вариант на enum) | по-старата програма отваря файла, ако може; ако не може — съобщава „made by a newer 3DCadCraft … update the program“, а не „повреден файл“ |

Ново **незадължително** поле (с `#[serde(default)]`) не вдига нито един номер: старите програми го пропускат, новите попълват стойност по подразбиране. Така бяха добавени всички промени досега — **миграция не е била нужна**.

**Тест със стари файлове** (`tests/compat.rs`): папката `tests/compat/r<N>/` пази проекти, записани от програмата на ревизия N, а `tests/compat/expected.json` — обема, броя стени, операции и скици при добавянето им. Всеки `cargo test` ги отваря, регенерира и сравнява. Правила:
- фикстура и нейните стойности **никога не се променят**, за да мине промяна; ако тестът падне, значи стари файлове се чупят → миграция;
- при нова ревизия се добавят файлове с новото в `r<нова>/` и се записват с `CADCRAFT_WRITE_COMPAT=1 cargo test --test compat` (записва само липсващите).

## 7. Как да го пробваш

```bash
cargo run --example make_project -- /tmp/bracket.3dcadcraft   # създава проект през API-то
unzip -l /tmp/bracket.3dcadcraft                              # виж вътре
ls /tmp/bracket.src.3dcadcraft/documents                      # разпакуваната форма
cargo run -- /tmp/bracket.3dcadcraft                          # отваря го в GUI
```

В GUI панелът **File** има **Save** (един файл), **Save as folder** (папка) и **Open** (приема и двете).

## 8. Обмен с други програми (не е родният формат)

Родният формат пази *параметричния* модел. За обмен ще има отделни експортери/импортери:

| Формат | Посока | Приоритет | Бележка |
|---|---|---|---|
| STEP AP242 (`.step`/`.stp`) | внос/износ | **висок** | индустриален стандарт за B-Rep; AP242 носи и PMI |
| STL / 3MF | износ | висок | 3D печат; 3MF пази единици и цветове |
| DXF | внос/износ | среден | 2D скици и разгъвки от листов метал |
| PDF | износ | среден | чертежи |
| IGES | внос/износ | нисък | стар, но още се среща |
| OBJ / glTF | износ | нисък | визуализация, уеб |
| `.ipt`/`.iam` | — | не | затворен формат на Autodesk; обменът минава през STEP |
