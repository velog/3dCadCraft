# 0.20 Large models: levels of detail, instancing, Undo deltas, parallel and background work

## 1. Purpose

A design of a few hundred parts, or one imported file with hundreds of bodies, must stay as quick to
look at, hover, pick and edit as a small one (rule 20: a pick, a hover or an OK within 100–200 ms,
an idle or hovering frame within ~16 ms). Today several costs grow with the whole model where they
should grow with what changed or with what is seen:

- an assembly's scene is one world-space buffer of every occurrence's triangles, built on the CPU
  and uploaded whole after each change that touches the scene;
- every triangle is drawn at the one display tolerance (0.01 mm chord), however small it is on
  screen;
- Undo keeps up to 100 full copies of the project, each with every body and display mesh;
- features, parts and files are rebuilt one after another on one thread, and the OK of a command
  (and Rebuild All, Open) runs on the main thread, so the window freezes while it works;
- hovering a model of many bodies does work per frame that grows with the body count.

The owner's case is an imported board, *KPB4*: 612 bodies, 465 occurrences as an assembly. In a
debug build, before the work in commit `4cd0875e`, a hover frame took 3.6 s as an assembly and
35 ms a frame as one multi-body part. That commit brought it to 40 ms per hover-change frame, no
idle frames, 350 ms per selection click, and 12–26 ms a frame as a part. This spec takes over from
there.

This is a mechanism, not one command: a few options in Application Options, a status-bar hint, and
otherwise no change to what the user does. Each part below gives Inventor's behaviour (in our own
words), how others solve it, where it goes in our code, the risks, the perf cases with budgets, and
the order of work.

## 2. Inputs

- the active document: a part (one or many bodies), an assembly (occurrences, subassemblies,
  linked part files through `LibCache`), a drawing (views of either);
- the camera: view matrix, viewport size in pixels, which parts are inside the view;
- the edit history (`command::History<Project>`) and the action that is about to change the project;
- the feature list of a part and its dependencies (`part::history::feature_refs`), the documents of a
  project and the files they link;
- application settings (`AppOptions`), new ones listed in §3.

## 3. Settings and behaviour

### 3.1 Levels of detail (LOD) for large assemblies

**Inventor.** Inventor keeps the frame rate up in two ways. While the view moves it simplifies what
it draws (Application Options › Display: a minimum frame rate, below which detail is dropped during
navigation, and a display quality setting). For whole large assemblies it offers Express mode: the
assembly opens from cached display data, with a reduced command set until full data is loaded.
Separately, a model state (Level of Detail in older releases) can suppress components to make the
assembly lighter. Representations and model states are ours already (spec 3.9). This section is
about the display only.

**Others.**
- SolidCraft (MIT/Apache) makes display levels for any mesh of 20 000 triangles or more, on up to
  two worker threads (`crates/ui-egui/src/mesh_lod.rs`). It uses quadric-error edge collapse
  (Garland and Heckbert, "Surface Simplification Using Quadric Error Metrics", SIGGRAPH 1997), as
  solidcore-tess `simplify::levels` implements. Each level keeps its measured error in mm.
- Per placement, each frame, SolidCraft draws the coarsest level whose error stays under 0.75 px
  where it lands on screen (`viewport-gpu` `LOD_PX`, `placement_scale`, `level_for`). A placement
  whose box is outside the view is not drawn (`Batches::cull`, `placed_box_in_view`).
- Picking, measuring and export never read a simplified mesh.
- The usual alternative is screen-size culling: a whole part drawn as nothing, or as its box, when
  it covers fewer than N pixels. Our drawing views already have "hide parts < 30 mm" for 100 000
  components (`tests/perf_drawing.rs`).

| Option | Inventor behaviour | Ours | Status |
|---|---|---|---|
| Levels of a large mesh | detail dropped during navigation | each part document's display mesh above 20 000 triangles gets 2–4 coarser levels with their error (QEM, made on a worker thread once per body state, kept with `material::cached_mesh`); drawn in full until ready | ⬜ |
| Choosing a level | by frame rate | per occurrence per frame: the coarsest level whose error is under 0.75 px at its nearest point to the eye (SolidCraft's rule); a fixed rule, so a still view does not change and nothing flickers | ⬜ |
| Culling | — | an occurrence whose placed box is outside the view frustum is not drawn (its instances leave the draw list, §3.2) | ⬜ |
| Small parts while navigating | detail dropped below the minimum frame rate | Application Options › Display › *Hide parts smaller than N px while the view moves* (off by default): such occurrences are left out during orbit / pan / zoom and drawn again on the frame after | ⬜ |
| Express open | assemblies above N files open from cached graphics | not in this stage: we keep no saved display meshes. Open stays full, but in the background (§3.5) | ⛔ needs saved display data (ROADMAP K14) |
| What reads it | display only | picking, Measure, Interference, export and drawings always use the full mesh | ⬜ |

**Where in our code.**
- New module `kernel::simplify` (GUI-free, testable in `tests/perf.rs`): QEM levels of a
  `SolidMesh`, error measured as SolidCraft's is. Either our own implementation, or solidcore-tess
  (Apache-2.0, in solidcore's workspace at `3e338c2`; it depends on a newer `solidcore-record` than
  the one we pin, so it comes with the kernel catch-up). An `ATTRIBUTION.md` row if adapted.
- `gui/material.rs`: `cached_mesh` keeps the levels beside the mesh (`Arc<Vec<(Arc<SolidMesh>, f32)>>`).
- `gui/renderer.rs`: per-instance level choice and culling in a `cull(view, size)` step before
  `render`, next to the instance buffers of §3.2.
- `gui/assembly.rs::assembly_scene`: the occurrence's box for culling (`assembly::PickMesh` bounds
  exist already).

**Risks.**
- A level must not change silhouettes users measure by eye. An error of 0.75 px is below what MSAA
  4× resolves; edges stay full (they are lines, and few).
- A thin wall can collapse into a hole at a coarse level. QEM with boundary planes (as solidcore-tess
  does) and a fold test keep this rare. A level whose error exceeds 1 % of the part's box is dropped.
- Memory: 2–4 levels add at most ~1.3× the full mesh (each level at most a quarter of the one before).
- Section views (`renderer::Cut`) and Slice Graphics draw the full mesh: a cut face must be exact.

### 3.2 Instancing: one GPU mesh for repeated parts

**Inventor.** Not exposed. Every viewer of large assemblies shares a part's graphics between its
occurrences.

**Others.**
- SolidCraft's `InstancedMesh` (`crates/viewport-gpu/src/view.rs`): the part's triangles in its own
  frame are uploaded once (`SharedTris`, keyed by a hash of the triangles). Each occurrence adds 52
  bytes: the 3 × 4 rows of its rigid move and a palette index for its colour.
- Moving, recolouring or hovering an occurrence rewrites only the instance buffer.
- See-through and faded occurrences are separate instance lists drawn after the opaque ones.
- This is standard GPU instancing (`draw_indexed(.., 0..instances)` with a per-instance vertex buffer).

| Option | Ours | Status |
|---|---|---|
| Mesh per part | one GPU triangle and edge buffer per (part document, body signature, appearance set) in part coordinates; a 20 000-bolt assembly holds one bolt mesh | ⬜ |
| Placement | per occurrence: its world transform (3 × 4 f32) + a palette index (tint, selection, hover colour) | ⬜ |
| Hover, selection, transparency | change the palette index or move the instance to the see-through list: no mesh rebuild, no full upload (a selection click is 350 ms today on the board) | ⬜ |
| Per-face overrides | an occurrence with its own face appearances (`Occurrence::looks`), a part cut by assembly features (`AsmUi::cuts`) or adapted in place keeps its own baked mesh, as today | ⬜ |
| Edges | instanced the same way (line list per part, per-instance transform); the visual style's dashed hidden edges unchanged | ⬜ |
| Cosmetic threads | stay baked (one mesh for every occurrence, `occurrence_threads`): few triangles | ✅ (unchanged) |

**Where in our code.**
- `gui/renderer.rs`: an `InstancedMesh`-like `PartBatch { key, tris, edges, instances }` with its own
  GPU buffers, kept across uploads while the key is the same. `upload` takes the baked
  `SceneGeometry` (sketches, overlays, previews) plus the batches.
- `gui/viewport.wgsl`: a vertex shader that reads the instance rows and transforms position and
  normal (rigid: the same rotation). The `clip` uniform of Slice Graphics and the section `Cut`
  stay in world space, after the transform.
- `gui/assembly.rs::assembly_scene`: instead of `add_occurrence_mesh` + `g.append` per occurrence,
  one batch per component and one instance per shown occurrence. `ASM_SCENE` and
  `occurrence_scene_key` remain only for occurrences that keep baked meshes.
- `gui/asm_select.rs::asm_hover_overlay`: the hover is a palette change, and the lifted overlay goes.
- Subassemblies: every leaf (`assembly::tree::leaves_in`) is an instance with `place * l.world`.

**Risks.**
- egui-wgpu draws our offscreen texture. The instance buffer must stay under `max_buffer_size`, as
  the existing `gpu()` check does (52 B × 100 000 = 5.2 MB, far below it).
- The red back-face pass (`backfaces_under`) needs the same instancing, or orientation bugs show
  only on baked meshes.
- Mirrored occurrences (`assembly::replace` mirror = a copy part) are separate parts, so no negative
  determinant reaches the shader. A test asserts every instance transform is rigid.
- The colour moves from the vertex to a palette entry. Per-face appearance colours of the part
  itself stay in the vertex, and the instance's palette entry tints them as `FaceOver::tint` does now.

### 3.3 Undo as deltas instead of full snapshots

**Inventor.** Undo is unlimited within a size budget: Application Options › General has an undo
file size, and the undo data lives in a temporary file. Some long operations clear it.

**Others.**
- The common designs are commands with inverse operations (the Command pattern; ROADMAP A9,
  FEATURES 0.4), or snapshots with structural sharing (persistent data: a copy shares every
  unchanged piece, as immutable collections and copy-on-write trees do).
- solidcore's own `Brep::snapshot` / `clone_sharing_surface_caches` became copy-on-write arenas in
  our fork's first fix (vendor/README.md), and made a snapshot cost the same on any B-rep.
- Our diagnostics journal already stores part states as JSON deltas (`diagnostics::journal::diff`).

| Option | Ours | Status |
|---|---|---|
| What a step holds | stage 1: the project with structural sharing: each document behind `Arc` (copy on write), each part's `body`, `exact_bodies` and display meshes behind `Arc`. A checkpoint copies pointers, and an edit copies only the document it changes. Stage 2: the serialisable `Command` enum (FEATURES 0.4), with commands and deltas stored | ⬜ |
| Size limit | Application Options › General › *Undo memory (MB)*, default 1024; the oldest steps go first, never the last one; the step count limit (100) stays as a second bound | ⬜ |
| What it measures | a step's own bytes (what it does not share with the next state), estimated from the documents it copied | ⬜ |
| Coalescing, labels, `break_coalescing`, `generation`, Undo / Redo menus | unchanged (rule 4) | ✅ (unchanged) |
| Display meshes | never part of a step: they are rebuilt or found in `cached_mesh` by body signature | ⬜ |

**Where in our code.**
- `document::Project` (`documents: Vec<Document>` → `Vec<Arc<Document>>` with `Arc::make_mut` in
  `document_mut`, or the same inside `DocumentData::Part`).
- `part::PartDocument::body` (`BRep`) and `Face::mesh` behind `Arc`, so a clone of an unchanged
  part copies no triangles.
- `command::History` gains byte accounting (`record(label, before, bytes)`).
- `CadCraftApp::checkpoint` stays the one entry point.

**Risks.**
- Code that mutates a cloned part in place (preview copies, `edit_part`, `docs_edit`, `asm_try`)
  must go through `make_mut`, or it writes into the shared snapshot. Compile errors find most of
  these sites; a test checks every Undo step reproduces its recorded state (journal replay).
- `serde(skip)` runtime fields (`work`, `holes()`, caches) must survive a shared clone: they are
  inside the shared value, so they do.
- Linked files' edits (`Project::linked_edits`, already `Arc`) keep working.

### 3.4 Parallel regeneration of independent features and parts

**Inventor.** Parts of an assembly update in turn. Drawing views can update in the background
(raster views first, precise lines after).

**Others.**
- SolidCraft builds a body's faces in parallel (`solidcore-tess` `par.rs`) and runs at most two
  LOD jobs at once.
- The general rule (task graphs, as build systems schedule targets): run in parallel what has no
  path between it in the dependency graph, join in history order.
- Our dependency graph exists already (`part::history::feature_refs`, `Feature::sketch_ids`), and
  per-document work is independent (rule 8: a part regenerates from its own features only).

| Level | Ours | Status |
|---|---|---|
| Documents of a project | `Project::rebuild_unmeshed_parts`, Rebuild All of an assembly, Make Components' `update_derived`: every part document that needs it is rebuilt on its own thread (at most the core count minus one), joined in project order | ⬜ |
| Linked files | `LibCache::prefetch` already loads files off the main thread | 🟡 (one worker per file; checked 2026-11) |
| Bodies of one part | tessellation of each solid (`cached_mesh` misses, `PickCache::build`) on scoped threads | ⬜ |
| Features of one part | the tool of each feature (an Extrude's prism from its sketch, a Hole's revolved tools) is made in parallel where it does not read the body; the Booleans stay in history order. A feature that reads the body (Fillet, Shell, Draft, To Next) is a barrier | ⬜ |
| Determinism | results are joined in history order, so names, volumes and the `BuildCache` keys are those of the sequential build (rule 8) | ⬜ |

**Where in our code.**
- `document::Project` (a `rebuild_parts_parallel` used by `rebuild_unmeshed_parts` and Rebuild All).
- `part/mod.rs::build_features` (a pre-pass making independent tools with `std::thread::scope`, as
  `kernel/exact.rs` already does for slabs and patterns).
- `gui/material.rs::cached_mesh` (a batch tessellation entry point).

**Risks.**
- The 64 MB main-thread stack (`build.rs`) does not apply to workers. Kernel calls on workers need a
  `std::thread::Builder::stack_size` of 64 MB, as the OK path would abort on a stack overflow.
- `BuildCache` is a `Mutex<Vec<..>>` shared by clones: per-document caches are independent, but a
  per-feature pre-pass must not hold the lock across kernel work.
- Thread-local caches (`MESHES`, presearch grids) are per thread: a worker's tessellation must hand
  its mesh back to the main thread's cache.
- Memory: N parallel regenerations of large parts multiply peak memory; the thread count is capped
  and a part above a size estimate runs alone.

### 3.5 OK and Rebuild All in the background

This is spec 0.19 §3.3, taken here because it shares the worker infrastructure.

| Step | Ours | Status |
|---|---|---|
| OK of a command | the command's feature is applied to a copy of the part on a worker thread (the copy is cheap with §3.3). Until it is ready the view shows the old body with the progress bar (0.19 §3.1), the command panel stays open and disabled, and the result is taken in one Undo step (`checkpoint` at take time, with the state before the OK) | ⬜ |
| Preview reuse | an OK whose preview already built the same thing takes the preview's part (`take_preview_part`), as Pattern does now: no second build | 🟡 (Pattern only) |
| Rebuild All, Open | the same: the part or every part (§3.4) on workers, the old state shown until then | ⬜ |
| Edits while it runs | the view can be orbited, hovered and measured; commands that change the document wait (the `open_state` check gains *a job is running*) | ⬜ |
| Failure | the feature's error as today (`<Command>: <reason>`), the part unchanged (rule 5), the bar cleared | ⬜ |
| Cancel (Esc) | the job is dropped. The kernel is stopped where solidcore's `CancelToken` reaches (the smlib layer's `run` takes one) | ⬜ |

**Where in our code.**
- `gui/mod.rs`: `preview_async` / `preview_ready` grow into a general `jobs` slot (key, receiver,
  reporter).
- Each command's OK (`dialog_ok`, `sm_ok`, `hole_ok`, …) splits into *plan* (on the main thread:
  the feature definition, the Undo label) and *build* (the worker: `insert_feature` / `replace_feature`
  on the copy).
- `CadCraftApp::open_state` and `keys.rs` know the running job.
- The journal records `command_ok` when the result is taken.

**Risks.**
- Two copies of a large part at once (memory), unless §3.3 lands first. This is why it comes after
  stage 1 of Undo.
- The draft state of a command must not change between plan and take. The panel is disabled, and
  the take compares `part_signature` as `take_preview_part` does.
- Debug builds and tests run OK synchronously (one flag), so GUI-free tests keep their order.

### 3.6 Hover and pick cost on imported multi-body models

**Inventor.** A prehighlight follows the cursor at the display rate on any model. It can be
switched off (Application Options › General › Enable prehighlight, our `theme::hover_edge`).

**Others.**
- Viewers of large models pick with the GPU: an offscreen ID buffer (R32Uint) holding each
  triangle's face or body id, read around the cursor (one small copy, ~1 ms). Then picking cost no
  longer depends on the model.
- On the CPU side the standard structure is a spatially sorted BVH (SAH or median split), not runs
  in arena order.
- The rule used throughout `4cd0875e`: work only when the pointer, the camera or the model changed.

Done in `4cd0875e` (batch4-merge), to check in the app: frame trace spans and repaint causes in the
slow-frame log (`gui/frame_trace.rs`, `CADCRAFT3D_SLOW_FRAME_MS`), `ScreenMap`, `EdgeSet::near_ray` /
`SphereGroups`, `PickCache` chunk boxes, overlay buffers for hover and selection, the part's own
scene kept by signature, packed meshes kept per occurrence (`occurrence_scene_key`),
`History::generation` for the unsaved check, and `feature_uses_context` no longer serialising an
Import's STEP text every frame.

| Item | Ours | Status |
|---|---|---|
| Frame trace | spans and repaint causes in the slow-frame log | 🟡 4cd0875e (in the app on the board) |
| Hover without motion | `edge_under` and `candidates_under` run only when the pointer, the camera or the body key changed (6–9 ms a frame with a still mouse today); the last answer is kept | ⬜ |
| Select Other | no repaint every frame while it is shown: a repaint only on its timer or input | ⬜ |
| Pick structure | `PickCache` chunks and `SphereGroups` runs sorted spatially (a median-split BVH over the chunk boxes) instead of arena order; one `PickCache` per body, so a change to one body of 612 rebuilds one | ⬜ |
| GPU pick | optional ID buffer (face id + body id in an R32Uint target, drawn with the scene): hover reads the pixel under the cursor, edges keep the CPU test within the picked face's neighbours | ⬜ (after §3.2: it shares the instance buffers) |
| Selection click | 350 ms on the board (scene rebuild + upload): with §3.2 a palette change | ⬜ |
| Browser | a part of 612 bodies lists them through `ScrollArea::show_rows` (only visible rows built) | ⬜ |
| Per-frame serialisation | no `serde_json` of features in a per-frame path (to check: `part_signature` serialises the features, an Import's whole STEP text included; where it runs per frame it should hash the `Arc<str>` pointer and length instead) | ⬜ |

**Where in our code.**
- `gui/mod.rs`: `PickCache`, `EdgeSet`, `SphereGroups`, `edge_under`, `candidates_under`,
  `part_signature`.
- `gui/camera.rs::ScreenMap`, `gui/select.rs`, `gui/panels.rs` (browser rows),
  `gui/renderer.rs` + `viewport.wgsl` (the ID target).
- Moving `PickCache` and `SphereGroups` into a GUI-free `part::pick` module lets `tests/perf.rs`
  time them.

**Risks.**
- An ID buffer is one frame late after a camera move. The hover is taken from the frame drawn
  (fine for the eye), the click from a fresh CPU ray (exact).
- wgpu readback is asynchronous: map the 1 × 1 (or 9 × 9) buffer and read it the next frame, never
  block on it.

## 4. Browser and editing

- No document data changes: levels, instances, pick structures and jobs are runtime state. Undo
  steps are memory only, so there is no format revision.
- New Application Options (`AppOptions`, loaded field by field):
  - Display › *Hide parts smaller than N px while the view moves* (off, N = 4);
  - General › *Undo memory (MB)* (1024);
  - Part › *Build OK in the background* (on; off = today's behaviour, for comparison).
- The status bar shows the progress bar of background jobs (0.19 §3.1). While a job runs, the
  command panel says "Building…" and its OK is disabled.

## 5. Edge cases and errors

- A level that cannot be made (a mesh that collapses, a refused simplification) leaves the mesh at
  full detail. It is never an error to the user.
- An instance whose part has no mesh yet (a linked file still loading) is drawn when it arrives
  (`LibCache::ready`), as today.
- Undo memory too small for even one step: the newest step is kept anyway (a warning in the log).
- A background OK whose part changed meanwhile (another tab, a linked file reload) is dropped with
  "<Command>: the part changed while it was built; press OK again".
- A worker that panics: `diagnostics::crash::guard` turns it into the command's error. A stack
  overflow cannot be caught, hence the 64 MB worker stacks (§3.4).
- Parallel regeneration that fails in one document: that document's health as today, the others
  unaffected.

## 6. Implementation, perf cases and order of work

### 6.1 Perf cases to add

GUI-free cases go into `tests/perf.rs` (the `within(ms, budget)` helper, `median_ms`). GUI cases
need the renderer or `CadCraftApp` and go into `gui::` unit tests listed in `TIMED_UNIT`
(`xtask`), each run alone. Budgets are for the test profile on the reference machine (`docs/PERF.md`).

| Case | Measures | Budget |
|---|---|---|
| `kernel::simplify` levels of a 200 000-triangle mesh (a 32 × 32 hole plate's display mesh) | time, error of each level, triangle counts | ≤ 1.5 s on one worker; level 1 ≤ 1/4 triangles at ≤ 0.05 mm error |
| Instanced scene of 5 000 / 20 000 occurrences (`examples/big_assembly.rs` model, `gui::` test) | `assembly_scene` time, bytes uploaded | full build ≤ 150 / 400 ms; GPU bytes ≤ unique meshes + 52 B × N; a hover change ≤ 2 ms and ≤ 64 KB uploaded |
| Selection click on the 465-occurrence synthetic board (`gui::` test) | scene work per click | ≤ 16 ms |
| Visible triangles at Fit of 20 000 occurrences with LOD | triangles drawn | ≤ 2 M (without LOD ~20 M) |
| Undo checkpoint of a 612-body import (synthetic STEP fixture, below) | `checkpoint` time, bytes the step adds | ≤ 5 ms, ≤ 1 MB |
| Undo memory of 100 edits of the 36-hole plate | total bytes held | ≤ 64 MB |
| `rebuild_unmeshed_parts` of 24 parts | wall time against the sequential run on the same machine | ≤ 0.4 × sequential on ≥ 4 cores (a ratio, not ms: robust under load) |
| A part of 16 independent Extrude Cuts (sketches on the top face, no shared geometry) | regeneration with the tool pre-pass vs without | ≤ 0.6 × sequential; identical names, volume, faces |
| Background OK of the 32 × 32 hole pattern | main-thread time inside the OK call and per frame while it runs | OK returns ≤ 5 ms; frames ≤ 16 ms |
| Hover on the synthetic board as a part (`part::pick` once moved) | `PickCache` build, one ray pick, edges near a ray | build ≤ 300 ms; ray ≤ 1 ms; edges ≤ 2 ms |
| Idle hover (`gui::` test) | work in a frame with a still pointer, a still camera and a still model | ≤ 0.5 ms; no repaint requested |

The synthetic board is `examples/many_bodies.rs`: 600 boxes and 12 holed cylinders written once as
STEP into `tests/data/many_bodies.step` (a few MB; ours, no supplier data). The owner's file stays
private, and its numbers go in `docs/PERF.md` as checks in the app.

### 6.2 Order of work

Sizes as in ROADMAP (tokens of agent work, rough).

| # | Step | Depends on | Size |
|---|---|---|---|
| L0 | Finish and land `4cd0875e` (tests through `xtask`, the two open items: Select Other repaint, idle `edge_under`), the perf cases of §6.1 that measure today's state, the synthetic board fixture | — | S, ~60–100k |
| L1 | Undo stage 1: `Arc` documents and bodies, byte accounting, Undo memory option | L0 | M, ~150–250k |
| L2 | Instancing (§3.2) with palette colours, hover / selection as palette changes, culling | L0 | L, ~250–350k |
| L3 | Background OK, Rebuild All, Open (§3.5): the jobs slot, plan / build split of every OK, 64 MB worker stacks | L1 | L, ~250–400k (many commands) |
| L4 | Parallel regeneration of documents and tessellation (§3.4); the feature tool pre-pass last, behind a switch until its tests prove identical results | L3 (worker infrastructure) | M, ~150–250k |
| L5 | Levels of detail (§3.1): `kernel::simplify`, per-instance level choice, hide small parts while moving | L2 | M, ~150–200k |
| L6 | Picking at scale (§3.6): BVH, per-body `PickCache`, `part::pick` move, then the optional GPU ID buffer | L2 | M, ~120–200k |
| L7 | Undo stage 2: the `Command` enum and deltas (FEATURES 0.4, ROADMAP A9), also the MCP API's entry point | L1 | XL, separate plan |

Each step updates its rows here, `docs/PERF.md` (the log), ROADMAP (A6, A9, K13) and CLAUDE.md
(pitfalls), and is checked in the app on the owner's board and on the 20 000-occurrence assembly
(rule 16).
