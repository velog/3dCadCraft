# 3.1a Subassemblies

Status: spec written 2026-10-28 (owner's step 4 of the assembly order); S1 and S2 done 2026-10-28, S3 and S4 2026-10-29 (checked in the app with `cargo run --example subassembly_demo -- file [overlap]`).

## 1. Purpose

An assembly placed in another assembly as one component. Without it the BOM has one level, and
Interference, Pattern, Copy, Mirror and drawings never reach parts below the first level. Inventor
treats a subassembly as one rigid body in its parent by default. It can be made *Flexible*, so its
free components move in the parent, and components can be moved between levels (Demote /
Promote).

## 2. Inputs

- An assembly document of this design file or of a linked file, placed with Place like a part.
- Its own occurrences, relationships and patterns stay in it; the parent stores only the occurrence
  of the subassembly (placement, flags, appearance) and the relationships it makes to geometry inside.

## 4. Browser and editing behaviour

- The subassembly row has an Assembly icon; it folds open to its own components (by name), each with
  its eye greyed (visibility inside a subassembly is the subassembly's; a parent override comes with
  View representations, 3.9).
- Changing the subassembly (in its own tab) updates every parent that shows it on the next frame
  (linked files: reloaded when the file changes, as parts are).

## 5. Edge cases and errors

- A subassembly placed in itself, directly or through another one: refused at Place, and a file
  that has such a loop shows the inner occurrence as sick (*contains itself*), never recurses forever.
- A relationship to a part inside a subassembly whose path no longer exists (the subassembly was
  changed): sick, as a missing face is (rule 8).
- An empty subassembly: placed, drawn as nothing, its box is its origin.

## 6. Implementation

- `assembly::tree`: walks an assembly's occurrences recursively (`leaves(project, asm, f)` gives the
  path, the part's `DocRef` and the world placement) with the cycle guard; display, picking, BOM,
  Interference, Physical Properties and drawings iterate the leaves instead of the first level.
- Linked files: `tree::Linked` holds the project of every linked file the active file reaches (the GUI
  builds it from `LibCache`, `CadCraftApp::linked`). A linked assembly's own references are in its
  file's terms; the walk rebases them (`tree::rebase`: a local document of that file becomes
  `DocRef { library: <the link that reached it> }`, its own links keep their ids, which `LibCache`
  resolves next to that file). `Leaf::component` / `Nested::component` are the rebased references —
  never use `occurrence.component` of a nested occurrence.
- Order of work: S1 Place + display + Component picking + cycle guard → S2 BOM levels, Physical
  Properties, Interference → S3 relationships into nested parts (`GeomRef::sub`, format revision) and
  Part Priority → S4 browser and Open → S5 Flexible → S6 Demote / Promote.
