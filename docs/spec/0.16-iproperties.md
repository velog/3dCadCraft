# 0.16 iProperties: document properties

Status: ✅ done · 🟡 partial · ⬜ to do · ⛔ blocked by another feature.

## 1. Purpose

Every document — part and assembly — carries descriptive properties (title, author, part number,
description, revision, status…) and properties of the user's own (name, type, value). They classify and
find files and fill parts lists, bills of materials and title blocks (3.6, drawings). The owner asked for
them on 2026-10-24: the standard values for every document type and non-standard (custom) ones.

## 2. Inputs

- The document (the active one, a document of the browser, or a component of an assembly).
- Values typed by the user; defaults from the file (name, dates) and the user's login name.

## 4. Browser and editing behaviour

- Every change is one Undo step (typing in a field coalesces); the document becomes unsaved.
- The values travel with the document: Pack / Append copy them; a linked part keeps its own.

## 5. Edge cases and errors

- A custom property with an empty name, a name already used, or a standard name: refused with
  `iProperties: …`.
- A Number value that does not evaluate: the field shows the error and keeps the old value.
- Old files without properties open with empty values (the defaults still show).

## 6. Implementation

- `document::iprops`: `IProperties { standard: BTreeMap<key, String>, design_state, custom: Vec<CustomProperty> }`
  on `Document` (`#[serde(default)]`, skipped when empty: additive, older builds ignore it). The table
  `STANDARD` lists every standard key with its tab and label; `effective(key, file name)` gives the
  value with defaults (Part Number = file name).
- `IProperties::new_document()` fills Author, Designer and Creation Date for new documents.
- GUI `gui/iprops.rs`: the window with its tabs.
