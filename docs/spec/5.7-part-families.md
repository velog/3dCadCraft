## 1. Purpose

One part with a table: each row (**member**) is a size or variant. Parameters, Properties, suppressed features
and threads change per row. A bolt with M6 / M8 / M10 and its lengths is one file.

## 2. Inputs

A part with named parameters. Manage › Author › Create Part Family (`CPF`).

## 4. Browser and editing behaviour

The table belongs to the part. Activating a member is not an edit of the model: it applies the row's values and
regenerates, with the usual Undo step. Editing a feature while a member is active changes the template.

## 5. Edge cases and errors

- A cell that cannot be evaluated, or a parameter deleted while a column uses it: the Verify error, and health on
  the part until fixed (rule 8). The column is never dropped silently.
- A row that fails to regenerate: refused (rule 5), the previous member stays.
- Deleting the active row: the default row becomes active.
- A column using the name of a renamed parameter follows the rename, like equations.

## 6. Implementation

- `part::family`: `FamilyTable { columns, rows, active, default }`, on `PartDocument::family` with
  `#[serde(default, skip_serializing_if = "Option::is_none")]`: additive, no format revision.
- `Column { name, caption, unit, key_order, formula, custom, target }`; `target` is `Parameter(name)`,
  `Property(key)`, `Suppress(feature id)`, `Thread(feature id, field)`, `Material`, `Appearance`, `FileName` or
  `None`. Features by id and parameters by name, never by index (rules 2, 3).
- Cells are strings evaluated with `part::expr` against the other columns (units checked, `+` joins text); a
  column may have one formula for all its rows (6.3 §3.7).
- `FamilyTable::apply(&mut PartDocument, row)` sets parameters through `set_parameter_expr`, suppressions through
  the history code, then `regenerate()`; `BuildCache` makes going back to a known row cheap.
- **Rule 8:** a placed member is a *generated part of its own* (6.3 §6.2), so no occurrence holds per-instance
  state and the table's active row never changes what another assembly shows.
- **Model States (3.9) and assembly families:** the column `target`s are general enough for them; FEATURES 5.7's "one
  mechanism" holds. An assembly family needs its own targets (include / exclude a component), to be added with it.
- CSV read and write of the table is the spreadsheet route (Inventor: Edit via Spreadsheet), no Excel link.
- GUI: `gui/ipart.rs` replacing the planned panel. Tests: each `target` kind, keys narrowing, save / load, face
  names stable across rows, failure leaves the state unchanged, a `tests/perf.rs` case per 100 rows.
