## 1. Purpose

Components are placed from a library instead of being modelled: bolts, nuts, washers, pins, rivets,
bearings, keys, circlips, structural shapes, and the user's own parts. A **family** is one parametric
template and a table of sizes; choosing a row makes (or reuses) a part file. The parts carry their
designation, standard and material, so the BOM and drawings name them correctly.

Two sides, and the second is what makes it more than a parts catalogue:

- **Consuming**: Place, AutoDrop, Change Size, Replace, Refresh.
- **Defining**: Create Part Family (a family table in a part) → Component Authoring (what the part *is*: its
  category, the parameters a tool may read, how it connects) → Publish (into a writable library) →
  Library Editor (edit tables, categories, libraries).

## 2. Inputs

- Libraries: categories → families → members (table rows).
- Placing: a place in the assembly; for AutoDrop a target (hole edge, shaft, face).
- Defining: a saved part or part family, or an assembly (Publish Assembly, new in 2027).

## 4. Browser and editing behaviour

- A standard part is an occurrence of a read-only file with its own browser icon; Open shows it read-only.
- Its menu adds Change Size, Replace from Library, Refresh Standard Components (rule 17).
- As Custom gives an ordinary part; the link to the family is dropped.

## 5. Edge cases and errors

- A row removed from the family, or a library missing: the placed part keeps working from its file
  (status *Not Available*); only Refresh and Change Size are affected.
- The cached file missing on another computer: rebuilt from the family if the library is there, else health
  on the occurrence, like any missing link. Pack embeds members so a package needs no library.
- A row that fails to regenerate: refused with `Place from Library: <family> <key>: <reason>`,
  nothing placed (rule 5), never a half-made file in the cache.
- Two members with one file name: refused when the table is verified, not at placement.
- Change Size that loses a referenced face: the relationship goes sick as usual (rule 8). Members of one
  family must therefore name faces the same way, which template parts do by construction.
- A family template using a parameter missing from a row: found by Verify.

## 6. Implementation

### 6.0 Sample library (stage CC-S, 2026-11-02)

`data/components`: `categories.csv` (28 categories), `types.csv` (110 types, each naming its builder and its columns),
`families.csv` and `families/*.csv` (nominal values, decision 1 still open). `components::samples` reads them: 869 members of 36
families whose type has a builder (hex bolt, socket head screw, hex nut, washer, rivet, pin, key, retaining ring, ball bearing,
structural shape); the other types wait in the tables. A member is written when first asked for into
`<settings>/library/Samples/<category>/<family>/<designation>.ccpart` (`CADCRAFT3D_LIBRARY_DIR` redirects the library). An
existing file is replaced only when what it was made from changed (§6.2), and a file's project and document ids are derived from its designation: a library deleted and
written again still resolves every assembly's links. Assemble › Place from Library lists them; a part is linked by a relative
path, several occurrences share it, and its Part Number is the designation. What it showed for the tables:

- A link is a relative path, so a library in the settings folder makes an assembly point out of its own folder: on another
  computer the part is `(missing)` until Pack embeds it or the cache can rebuild it (§5, §6.2).
- The file works as a member with nothing new: **tables only have to produce these files**, which supports §6.1 and §6.2.
- Numbers are nominal and typed for trying it out: each part says so in Comments (decision 1 is still open).
- Hexagons are built directly, chamfered at the Full level by an exact cone (§6.0b): a bolt ~5 ms, ~10 ms chamfered.
- Every link regenerates its file on load, so opening an assembly costs the sum of its distinct parts: ~5–10 ms a bolt size (§6.0b).
  Storing the evaluated model (ROADMAP, SolidCraft catch-up item 3) would remove it.
- Members are generated on demand (§6.2): 869 are listed, only those used become files.

### 6.0a Levels of detail (owner's request, 2026-11-02)

The user chooses how much geometry a placed component holds; it is one component at every level (one designation, Part Number
and BOM row), so a large assembly can use Simple bolts without a different parts list.

| Level | Shape | Our status |
|---|---|---|
| **Simple** | one revolve: the envelope, without thread, socket or hexagon faces | 🟡 2026-11-02 in the window, waiting for a visual check |
| **Standard** | the usual shape with a cosmetic thread (2.9) | 🟡 2026-11-02 |
| **Full** | where it differs: hexagon corners cut at 30° by an exact cone (§6.0b); a bearing's two rings with their grooves and every rolling element a body of its own, as many as fit its pitch circle, two rows where the type has two (self-aligning, spherical roller). A tapered bearing's raceways and rollers are cones with one apex on the axis; a spherical roller bearing has a spherical outer raceway, a cone under each row and barrels leaning against the sphere. The other details of §6.5b (`samples::Finish`) | 🟡 2026-11-03 owner's request; circlip lugs, modeled threads ⬜ |

Each level is its own file (`<designation> (Simple).ccpart`) with its own derived ids. Changing the level of a placed part
(through Replace, keeping its relationships) ⬜. A family published by a user has its one shape.

### 6.0b Direct construction of fasteners (owner's request, 2026-11-02)

A hexagon joined to a shank took the kernel's Boolean ~240 ms of a part's ~245 ms (the display mesh 1.5 ms, the conversion
to our B-rep 3 ms), its corner chamfers 1.3–2 s. A fastener is therefore one `BodyOp::Axial`: its meridian as a chain of
runs, built face by face without a Boolean (`kernel::exact::axial_stack`).

| Item | Behaviour | Our status |
|---|---|---|
| Turned run | lines and arcs in (radius, z) revolved fully about Z; an end on the axis is a tip (a dome), any other end a ring | ✅ 2026-11-02 |
| Hexagon run | across flats, corners on +X, flats at ±Y; either way along Z (a head, a socket) | ✅ 2026-11-02 |
| Planar faces | between two runs at one height the two rings bound one face (a seat, a socket's rim); at an end of the chain a disc; `closed` joins the last run back to the first (a nut's bore) | ✅ 2026-11-02 |
| Chamfered hexagon (Full) | a cone from a circle of 0.95 s at 30° meets each flat in a hyperbola, an exact rational quadratic; the cone is one sector per corner, its rulings at the corners | ✅ 2026-11-02 |
| Face names | `<feature id>:<role>` (`Axial1:Shank`, `Axial1:Flat:3`, `Axial1:HeadChamfer`): the template gives the roles, so all sizes of a family have the same names (Change Size) | 🟡 by test on every family; the view shows only the feature's name |
| Cosmetic thread | finds its cylinder as before, and a thread longer than the shank's cylinder takes all of it (ISO 4014 M36 x 80: b = 78, cylinder 76.4) | ✅ 2026-11-02 M8 in the view; M36 x 80 by test |
| Old parts | parts saved with Revolve / Extrude stay as they are; only newly written members use this | 🟡 by the compat fixtures; no old library file opened in the view |
| Budget | 50 ms a part with its display mesh, at every level (`tests/perf.rs`, `library_fasteners_build_directly`) | ✅ 2026-11-02 worst 33.7 ms |

Edit Feature is disabled on this feature (its size comes from the table; Change Size, §6.2, replaces it).

Edge cases: a circle lying between a hexagon's flats and corners, two runs not meeting at one height, and a chamfer circle past
the flats are refused by `AxialOp::validate`. The body is ordinary for later features: a hole cut across a shank goes through
the kernel's Boolean.

### 6.1 Module and data model

New GUI-free module `components` (its samples exist, §6.0):

```
components/library.rs   LibraryRoot: folder, library.json (id, name, read-only), category tree
components/family.rs   FamilyInfo: stable id, name, standard, organization, revision, category, source
components/source.rs   FamilySource: Template(part with a FamilyTable) | Sections(frame table adapter)
components/member.rs   resolve row → template + values → regenerate → Properties → cached file
components/author.rs   Authoring: category, category parameter → column | parameter | value, connections
components/search.rs   index over names and key values
```

`FamilyTable` itself lives in `part::family` (spec 5.7), because a part family needs no library.

**A family is a `.ccpart` with a family table and a little metadata.** Create Part Family makes it, Publish
copies it into a library folder and adds `FamilyInfo`. There is one mechanism for part families and library
families, a template is an ordinary part anyone can open and edit, and it needs no new file type. A library
is a plain folder that works in git:

```
<library>/library.json
<library>/Fasteners/Bolts/Hex Head/ISO 4017.ccpart      (template + table + FamilyInfo + thumbnail)
```

Built-in families are written by Rust builders (like `Section::member_part`) and their tables come from
CSV under `data/components/`, so no binary files enter the repository and every builder is tested.

Our column and category parameter names are our own, taken from the standards' symbols (`d`, `l`, `s`, `k`,
`P`).

### 6.2 Files and references

- Document field `content: Option<ContentOrigin>` (library id, family id, family revision, key values, As
  Standard) with `#[serde(default)]`: additive, no format revision (rule 6).
- **Standard members are linked files** in the cache: `content_center` of the `.ccproj`, or by default the
  settings folder. Many occurrences share one file and `LibCache` loads it once. **owner** decision 2.
- `LibraryLink` checks the library's `ProjectId`, and `new_random` would make a rebuilt member a *different*
  project, so a member's id must be **derived from family id + key values**: the same member rebuilt
  anywhere resolves. Regeneration must be deterministic (rule 8).
- Refresh compares `ContentOrigin::revision` with the family's.
- Built-in members: a `.stamp` beside the file holds what it was made from (`catalog::BUILDERS`, the table's numbers, the detail). A different stamp writes the file again when it is next asked for, with the same ids: a corrected table reaches placed parts too. Until 2026-11-03 such a file was never replaced.
- Saves are atomic; a member is written under a temporary name and renamed, so two sessions can share a cache.

### 6.3 Profiles

Keep `profiles.csv`, `Section` and the user folder: the frame code depends on them, and they are fast and
exact. `FamilySource::Sections` shows the same data in the tree under *Structural Shapes* (families, sizes,
a custom `G_L` length). Insert Frame keeps its drop-downs. So one table feeds both, with no migration and no
change to old files. Added on top:

- `Section::member_properties` also writes part number and standard (BOM);
- each family gets a revision, which gives `FRF` its comparison;
- Structural Shape authoring (CC6) adds a parametric template family next to the fixed shapes; `AFP` stays as
  the quick path.

### 6.5a Smart Drop (2026-11-03)

`components::fit` decides without a window: `Fit::of(kind)` says how a member goes (into a hole, over a shaft, a
bearing, by hand), `choose(fits, target)` takes the nearest diameter and then a length (through a hole the shortest
that passes, in a blind one the longest that stays inside); a tapped hole's thread beats its drill.
`gui/smart_drop.rs` turns the item under the cursor into a `Spot` (once per item) and places the member with
**two relationships to the part's origin**: Mate of the target's axis with its Z axis, Flush of the target's plane
with its XY plane (Mate when flipped). All sizes of a family share that origin, so Change Size keeps them, where
edge names and hints would have to match between sizes. A countersunk head's seat sinks by its height.

### 6.5b The other types (from 2026-11-03)

Order, owner: a type with a placement of its own is added first, its Smart Drop after. Each type gets a table from a public source
(`data/components/SOURCES.md`) and a builder. Details the Standard level leaves out, since they cost a Boolean or change nothing in a BOM, are at the **Full level** (`samples::Finish`, 2026-11-03):
a screw's slot (DIN 84, 85; a slot across a dome took the kernel 4-5 s, so DIN 85's Full head is a short cylinder, a cone and a flat middle), the carriage bolt's square neck (one stepped body: a polygon run with `sides` 4; a Join took up to 16 s), castle slots (DIN 937), four slots in a round nut's rim (DIN 1804, DIN 981; a prism), teeth (DIN 6797, flat, not twisted; a prism), the taper washer's 8 % slope and the taper key's 1 : 100 (a prism with a tilted end, DIN 434, DIN 6886), the spherical seat (DIN 6319), threads at both ends with a plain middle (DIN 938), a cotter pin's split and round head (DIN 94; its head is no bent loop). Their proportions where the table has no column are ours: neck 1.08 d x 0.6 d, slots half the head, castle slots 0.38 m. Still left out: cross recesses, a blind rivet's mandrel. Smart Drop:
all of these as their kind. The T-slot nut (DIN 508) goes by a slot's floor (`Fit::Slot`, 2026-11-03): pausing on a long planar face takes its width from
the face's points (`fit::slot_floor`, a slot at any angle), the widest foot that fits, up to 1.35 times the foot; it stands on the floor with X across the slot, its middle on the slot's middle line (Flush with the floor, Flush with the long wall at half the width), free to slide along the slot.

Flanges (EN 1092-1 PN 16: Type 11 weld neck, Type 01 slip-on, Type 05 blind) and butt-weld fittings (ASME B16.9: 90 and 45 degree elbows,
tee, concentric reducer, cap) have a placement of their own: `Fit::Butt`, a part standing on the end of a cylinder of its own diameter and
continuing it, within 2 % (`BUTT`), since pipe series differ a little. A weld neck flange and a fitting meet the pipe's outside diameter, a blind flange the
outside of a flange. A slip-on flange is `Fit::Over`: it runs back along the pipe, its face flush with the pipe's end.

A flange is one stepped body with its bolt holes in it (`AxialOp::holes`, kernel `axial_stack_drilled`): a hole's rings join the planar faces at
its ends, with no Boolean. Twenty holes cut from a revolved disc took the kernel about 5 s a part; DN 600 now takes 65-86 ms. A straight tee is built face by face too (`AxialOp::tee`, kernel `pipe_tee`): two equal cylinders meet in exact half ellipses touching at their ends, where the Boolean took 25-39 s (1.2 s with a branch 0.5 % thinner); now 17-40 ms. Its Simple level has no holes. Left out for
now: the corner radius between hub and disc, the weld bevel. A cap's head is the usual torispherical stand-in for its ellipse (crown 0.9 D, knuckle 0.17 D). Walls are STD of ASME B36.10;
other schedules are other families, when asked for. Checked in the app 2026-11-03: DN 100 found and placed on a pipe's end.

Also added: wing nut (DIN 315), slotted round nut (DIN 1804), eye bolt (DIN 444 B), tee-head bolt (DIN 261), square head with a collar (DIN 478), shoulder screw (ISO 7379, by its
shoulder), blind rivet (DIN 7337 A, a plain rivet's shape). Their heads and eyes go on with one Boolean each, 12-208 ms a part. An eye stands at least 0.1 mm wider than its shank: DIN 444 lists M27 and M30 with both 27 and 30, whose sides the shank would only touch, and the kernel finds no Union. A wing nut's wings and an eye's ring are plain plates; the round nut's slots are left out.

The rest of the 110 types went in together on 2026-11-03: DIN 32501 weld stud, DIN 71412 grease nipple, DIN 910 plug, DIN 319 ball knob from the pages; a computed
involute gear (a straight line between flank points, no fillet at the root); and threaded coupling, clinch nut and stud, hex standoff, cage nut, ball valve, sprocket, V-belt pulley, compression and extension spring (a coil; no hooks, no ground ends), profile rail and carriage (blocks), hose clamp (a band), tube cap, bridge handle, levelling foot, butt hinge (flat); what each table was compared with is in `SOURCES.md` (step 4 of the owner's order, 2026-11-03), and those with no standard or maker's table stay typed and say so. Fine pitches of plugs and grease nipples are not in the thread table, so those threads are plain.
By hand only: rail, carriage, handle, hinge. Gears, sprockets, pulleys and springs go over a shaft by their bore.

ISO 3601 O-rings (2026-11-03) are a family of their own beside Metric O-Ring.

A family's picture (owner's request, 2026-11-03): a bearing family shows its **section through the axis** (`components/icon.rs`), since from outside every bearing is the same ring; two rows show as two rows. Rods, rails and structural shapes are drawn cut short (`Sample::for_picture`), or the picture was a line.

### 6.6 Budgets (rule 20, `tests/perf.rs`)

Targets, none measured yet:

| Case | Budget |
|---|---|
| Open the window, 2 000 families indexed | ≤ 200 ms, on a worker after the first time |
| Search keystroke over 100 000 rows | ≤ 16 ms |
| A member already cached: load and place | ≤ 100 ms |
| A new member: regenerate and write (worker thread, preview meanwhile) | ≤ 500 ms |
| Change Size of 100 occurrences of one member | ≤ 200 ms + one solve |
| Smart Drop hover, resize to the nearest size | a frame; members generated once and cached |
| Refresh analysis of 1 000 occurrences | ≤ 200 ms (compares revisions, generates nothing) |

Over budget, open: a 90 degree elbow above NPS 14 takes 525-600 ms (measured on a loaded machine): the time is the display mesh of its two torus faces, and a coarser mesh for large bodies would change old files' volumes. A spring's helix costs about 40-75 ms a turn at Standard, more when wound tight (7 close turns 526 ms, 20 turns 1.5-2.3 s), so the tables hold short springs (extension: 5 turns, compression: rows of 5.5 active coils); Simple is a tube.

### Risks

- **Data is the largest cost**, not the code: Inventor's library holds thousands of families and we cannot
  copy them. Decision 1 sets the pace, and CSV import lets users add their own suppliers' tables.
- **The kernel's cones** may make hex heads slow (§6.4). Measure in CC2 before typing more families.
- **Face names across sizes**: Change Size depends on them; a builder with an optional feature (a chamfer
  only above M6) would change names, so such options stay suppressed features, never missing ones.
- **Undo**: the cache is outside the project; a placed member's Undo removes the occurrence and leaves the
  file, which is harmless.
- `gui/place.rs` and `assembly::tree` assume a link is a user's file: the read-only state needs a check
  where linked edits are written (`save_linked_edits`).

### Open owner decisions

1. **Where the numbers come from.** Owner, 2026-11-02: manufacturers' published tables. Each table is compared with
   public sources and `families.csv` / `data/components/SOURCES.md` say with what; MISUMI's terms exclude it. Earlier
   recommendation: typed from the standards the owner has, or from
   manufacturers' published tables, each CSV naming its source. Never from commercial CAD (CLAUDE.md), and never
   from LGPL projects. Whether a table's numbers may be redistributed is worth the owner's check.
2. **Standard members: linked file in a cache (recommended) or a document embedded in the design file** as
   frame members are. Linked follows the file model the owner chose for assemblies and shares one file
   among 1 000 bolts; embedded makes every design self-contained but large.
3. **Order.** Recommended as above: own libraries (CC6) come after Smart Drop. If defining own components matters
   more than fasteners, CC6's Publish and table editor can move directly after CC2 without connections or Smart Drop.
4. **First set of families** for CC2 (proposal in the table), and whether ANSI is needed early.
